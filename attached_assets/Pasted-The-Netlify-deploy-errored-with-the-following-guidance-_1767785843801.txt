Diagnosis
- The build fails because esbuild (used during the Netlify Functions / server bundle step) is trying to bundle code that:
  1) uses a top-level await in vite.config.ts, which esbuild rejects when producing CommonJS output ([lines 105-108](#L105-L108)); and
  2) requires package artifacts that esbuild cannot resolve during bundling: "@babel/preset-typescript/package.json" and lightningcss's "../pkg" ([lines 119-127](#L119-L127)). These cause bundling to abort and make the Netlify Function dependency resolution fail (Netlify reports a function dependency error).
- Root causes:
  - Top-level await at module top-level (in vite.config.ts) — move the dynamic import inside an async function to avoid top-level await.
  - Missing or non-resolvable runtime files used by dependencies during bundling (either the packages are not present at the top-level package.json/node_modules or esbuild tries to inline modules that should be left external).

Solution — steps to fix
1) Fix vite.config.ts to remove top-level await
- Edit vite.config.ts to export an async config (wrap dynamic import inside the exported async function). This avoids top-level await at module scope and is compatible with bundlers that don’t support top-level await.
- Example change (replace your current top-level await import with this pattern). See your file: https://github.com/reyndeeev/BlessedUMC/blob/main/vite.config.ts

```ts
// vite.config.ts
import { defineConfig } from "vite";
import path from "path";

export default defineConfig(async () => {
  // move the dynamic import inside the async function
  const cartographerModule = await import("@replit/vite-plugin-cartographer");
  const cartographer = cartographerModule.default ?? cartographerModule;

  return {
    plugins: [cartographer()],
    resolve: {
      alias: {
        "@": path.resolve(import.meta.dirname, "client", "src"),
        "@shared": path.resolve(import.meta.dirname, "shared"),
        "@assets": path.resolve(import.meta.dirname, "attached_assets"),
      },
    },
    root: path.resolve(import.meta.dirname, "client"),
    build: {
      outDir: path.resolve(import.meta.dirname, "dist/public"),
      // ...your other build settings
    },
  };
});
```

2) Verify the problematic packages are present in the top-level package.json
- Before telling the bundler to externalize anything, verify that the packages are actually installed at the site root:
  - Check package.json for @babel/preset-typescript and lightningcss.
  - If they are missing, install them at the repo root:
    - For @babel/preset-typescript (dev dependency): npm install --save-dev @babel/preset-typescript
    - For lightningcss: npm install --save lightningcss
- Netlify requires function dependencies to be installed at the top-level package.json, otherwise they cannot be required at runtime. The build log also shows Netlify’s guidance: a function failed to require one of its dependencies ([lines 148-150](#L148-L150)).

3) If packages are present but esbuild still errors resolving internal files, mark them external so the bundler doesn’t try to inline files that are resolved at runtime
- After you confirm the packages are in package.json and installed, tell Vite/esbuild to treat these problematic imports as external. Add them to rollupOptions.external (or esbuildOptions.external) in your vite.config.ts build options. Example snippet to add inside the returned config from step (1):

```ts
// inside the returned config from defineConfig(...)
build: {
  // ...
  rollupOptions: {
    external: [
      "@babel/preset-typescript/package.json",
      "lightningcss", // externalize whole package so its runtime pkg/ files are not inlined
    ],
  },
  // optionally for esbuild:
  // commonjsOptions: { include: [] } or esbuild: { external: [...] }
}
```

- Important: do this only after you confirm the packages exist in package.json (see step 2). If a package is not installed, externalizing will only move the failure to runtime.

4) Re-run build locally and on Netlify
- Locally: npm ci && npm run build (or the commands Netlify runs).
- If you still get import.meta / CJS warnings: ensure that any code that must run in Node (server code / functions) is compiled with an ESM target or refactored to avoid import.meta usage at module top-level. The import.meta warnings come from bundling modules as CJS; the primary immediate blocker was the top-level await error.

If you hit Node version issues while testing on Netlify, you can change the Node version used by Netlify (see docs): https://docs.netlify.com/configure-builds/manage-dependencies/#node-js-and-javascript

Summary
- Remove top-level await by exporting an async config in vite.config.ts (move dynamic import inside the exported async function) — fixes the esbuild top-level-await error ([lines 105-108](#L105-L108)).
- Verify @babel/preset-typescript and lightningcss are present in top-level package.json and installed; if missing, install them.
- If esbuild still fails resolving internal package files, externalize those specific imports via rollupOptions.external after verifying the packages are installed.
